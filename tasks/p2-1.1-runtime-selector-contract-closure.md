# P2-1.1 Runtime Selector Contract Closure

## 0. 状态

```text
方案状态：已落地（Contract Closure）
阶段：P2-1.1
前置阶段：P2-1 DataDep Contract Closure
后续阶段：P2-2 DataDep Runtime Resolver
实施口径：未知 runtime.kind 一律 INVALID；UNSUPPORTED_RUNTIME_SELECTOR 不得携带非法 kind；删除 MISSING_USER_PATH / MISSING_PAGE_PATH；impl 与 accept-chain schema 对齐；禁止 user.path / page.path（含与 runtime 并存）。
```

本阶段用于修复 P2-1 已发现的 Contract Gap。

当前 P2-1 的问题是：

```text
DataDep 声明 resolved
↓
但 Runtime 仍然不知道如何确定性读取 Expected
```

尤其是：

```text
from = user
from = page
```

当前只有：

```text
user.path
page.path
```

不足以描述真正的 Browser Runtime 取值坐标。

---

# 1. 当前问题

当前 P2-1 Contract：

```json
{
  "paramKey": "ucid",
  "from": "user",
  "user": {
    "path": "user.id"
  },
  "status": "resolved",
  "unresolved": []
}
```

但仅凭这份 DataDep，Runtime 不知道：

```text
user.id
```

到底来自：

```text
window.__user.id
localStorage
Redux
React Context
登录接口
其他全局对象
```

因此：

```text
status = resolved
```

与：

```text
Runtime 可执行
```

并不等价。

这是 P2-1 Contract Gap。

---

# 2. P2-1.1 核心目标

修复后必须满足：

> 任意 `status = resolved` 的 DataDep，P2-2 只读取 DataDep 本身，就能够确定应该采用哪一种 Runtime 读取方式。

正式约束：

```text
resolved
=
source 已确认
+
runtime selector 已确认
+
selector 结构完整
```

不能再出现：

```text
业务语义已经知道
但 Runtime 不知道去哪取
```

---

# 3. 不改变当前正式主链路

仍然保持：

```text
events.json
↓
adaptor.json
↓
Parameter Resolution
↓
impl.json
↓
DataDep
↓
accept-chain.json
↓
Runtime Resolver
```

不增加第五个事实文件。

Runtime Selector 仍然属于：

```text
impl.events[].accept.dataDeps[]
```

并由 `build-accept-chain` 原样搬运到：

```text
accept-chain.paths[].targets[].dataDeps[]
```

# 4. Runtime Selector 的职责

Runtime Selector 回答：

> Browser Runtime 应该通过什么确定性坐标读取 Expected Source Value？

它不回答：

```text
业务参数最终如何计算
```

该职责仍属于：

```text
parameter.expression
parameter.sourcePath
```

例如：

```js
action.ucid = window.__user.id || '-'
```

Parameter 可以保存：

```json
{
  "expression": "window.__user.id || '-'",
  "sourcePath": "window.__user.id -> action.ucid"
}
```

DataDep 保存：

```json
{
  "paramKey": "ucid",
  "from": "user",
  "user": {
    "runtime": {
      "kind": "windowPath",
      "path": "__user.id"
    }
  }
}
```

二者职责不同。

---

# 5. 新增 Runtime Selector Contract

在 DataDep 的 source-specific 节点中增加：

```text
runtime
```

第一阶段统一结构：

```json
{
  "kind": "windowPath",
  "path": "__user.id"
}
```

语义：

```text
Runtime root = window
↓
getByPath(window, "__user.id")
```

---

# 6. 第一阶段 Runtime Selector Kind

P2-1.1 不一次性设计所有 Browser Runtime 数据源。

第一阶段只增加：

```text
windowPath
```

原因：

```text
能够被真实源码确认
+
Browser Runtime 可直接访问
+
P2-2 可以确定性执行
```

禁止为了完整性提前增加：

```text
redux
reactState
hook
context
dom
localStorage
cookie
indexedDB
apiCache
```

除非当前 repository 已经存在明确、稳定且需要 Runtime 验收的真实用例。

原则：

> 没有真实需求，不提前扩枚举。

# 7. User Contract 修正

旧结构：

```json
{
  "from": "user",
  "user": {
    "path": "user.id"
  },
  "status": "resolved"
}
```

不再允许作为 resolved。

新结构：

```json
{
  "paramKey": "ucid",
  "from": "user",
  "user": {
    "runtime": {
      "kind": "windowPath",
      "path": "__user.id"
    }
  },
  "status": "resolved",
  "unresolved": []
}
```

必须满足：

```text
user.runtime.kind != empty
user.runtime.path != empty
```

第一阶段：

```text
kind 必须为 windowPath
```

---

# 8. Page Contract 修正

Page 同样不能只写：

```json
{
  "page": {
    "path": "community.name"
  }
}
```

因为 Runtime 不知道 `community` 的 root 在哪里。

如果真实代码能够确认 Browser Runtime 可访问：

```js
window.__PAGE_DATA__.community.name
```

则 DataDep 可以是：

```json
{
  "paramKey": "community_name",
  "from": "page",
  "page": {
    "runtime": {
      "kind": "windowPath",
      "path": "__PAGE_DATA__.community.name"
    }
  },
  "status": "resolved",
  "unresolved": []
}
```

如果只知道：

```text
community.name
```

但不知道 Runtime root：

```text
status = needsConfirm
```

不能声明 resolved。

URL 当前：

```json
  "queryKey": "housedelCode"
}
```

本身已经是 Runtime 可执行 Selector。

因此 P2-1.1 不为了结构统一强制改成：

```json
{
  "runtime": {
    ...
  }
}
```

API 当前：

```json
{
  "from": "api",
  "api": {
    "urlIncludes": "/api/detail",
    "field": "data.price"
  }
}
```

同样已经具备基本 Runtime 可执行信息。

所以 P2-1.1 第一阶段只修：

```text
user
page
```

不要为了 Schema 对称做无价值重构。

# 10. resolved 定义正式升级

P2-1 旧定义：

```text
来源已经知道
+
selector 字段存在
```

升级为：

```text
来源已经知道
+
Runtime 读取方式已经知道
+
Runtime Selector 完整
+
无需 P2-2 二次推断
```

所以：

### URL resolved

必须有：

```text
queryKey
```

### API resolved

必须有：

```text
api.urlIncludes
api.field
```

### User resolved

必须有：

```text
user.runtime.kind
user.runtime.path
```

### Page resolved

必须有：

```text
page.runtime.kind
page.runtime.path
```

# 11. 新增 unresolved Code

建议新增：

```text
MISSING_USER_RUNTIME_SELECTOR
MISSING_PAGE_RUNTIME_SELECTOR
UNSUPPORTED_RUNTIME_SELECTOR
```

含义分别为：

```text
MISSING_USER_RUNTIME_SELECTOR
=
已知道是 user 来源，但不知道 Runtime 如何读取

MISSING_PAGE_RUNTIME_SELECTOR
=
已知道是 page 来源，但不知道 Runtime 如何读取

UNSUPPORTED_RUNTIME_SELECTOR
=
真实来源已确认，但当前 bella-tracking Runtime 尚不支持该读取方式
```

例如：

```json
{
  "paramKey": "ucid",
  "from": "user",
  "status": "needsConfirm",
  "unresolved": [
    "MISSING_USER_RUNTIME_SELECTOR"
  ]
}
```

# 12. Schema 修改

需要修改：

```text
schemas/impl.schema.json
```

增加：

```json
"runtimeSelector": {
  "type": "object",
  "required": ["kind", "path"],
  "properties": {
    "kind": {
      "enum": ["windowPath"]
    },
    "path": {
      "type": "string",
      "minLength": 1
    }
  }
}
```

User：

```json
"user": {
  "type": "object",
  "properties": {
    "runtime": {
      "$ref": "#/$defs/runtimeSelector"
    }
  }
}
```

Page：

```json
"page": {
  "type": "object",
  "properties": {
    "runtime": {
      "$ref": "#/$defs/runtimeSelector"
    }
  }
}
```

旧：

```text
user.path
page.path
```

建议删除，不继续兼容。

原因：

```text
兼容两套格式
↓
P2-2 又需要判断哪套是真的
↓
重新引入不确定性
```

# 13. Validator 修改

修改：

```text
scripts/accept/validate-data-dep.js
```

当前：

```js
if (from === 'user')
  return !!dep.user.path
```

改为：

```js
if (from === 'user') {
  return validRuntimeSelector(dep.user?.runtime)
}
```

Page 同理。

新增确定性函数：

```js
function validRuntimeSelector(runtime) {
  return (
    runtime &&
    runtime.kind === 'windowPath' &&
    str(runtime.path)
  )
}
```

禁止 Validator：

```text
解析 expression
解析 sourcePath
自动从 user.path 转 runtime.path
猜 window root
```

Validator 只能验证结构。

# 15. 重要边界：源码可访问 ≠ Runtime 可访问

例如业务代码：

```js
const user = useUserContext()

send({
  ucid: user.id
})
```

Parameter Resolution 可以确认：

```text
expression = user.id
sourcePath = UserContext → user.id
```

但 Playwright Runtime 不一定能直接访问：

```text
user.id
```

因此不能自动生成：

```json
{
  "runtime": {
    "kind": "windowPath",
    "path": "user.id"
  },
  "status": "resolved"
}
```

正确结果应该是：

```json
{
  "paramKey": "ucid",
  "from": "user",
  "status": "needsConfirm",
  "unresolved": [
    "MISSING_USER_RUNTIME_SELECTOR"
  ]
}
```

直到找到真实 Runtime 可读取证据。

# 22. Closure Criteria

只有满足以下条件，P2-1.1 才算 CLOSED：

```text
1. resolved DataDep 必须 Runtime executable
2. User/Page 不再只有业务语义 path
3. Runtime Selector 有确定 Schema
4. Validator 能确定性阻止 selector 不完整的 resolved
5. 不解析 expression/sourcePath 自动补 selector
6. build-accept-chain 只 copy，不推断
7. unsupported Runtime source 不允许假装 resolved
8. Claude Code / Codex / Cursor 对同一 DataDep 得到相同 Gate
```

最终保证：

```text
Parameter Resolution
负责确认事实

↓

DataDep
负责完整表达 Runtime 读取事实

↓

P2-2
只负责执行

↓

Runtime Expected
```

即：

> P2-1.1 的目标不是增加 Runtime 能力，而是保证 P2-2 不需要猜。
