# P2-2 Closure Patch：API Runtime Evidence Window

## 0. Status

```text
Phase: P2-2 Closure Patch
Current P2-2 Status: IMPLEMENTED / NOT CLOSED

Remaining Issue:
API Runtime Evidence Window starts too late.
```

目标：

```text
让 API DataDep 能读取 sharedSteps 阶段产生的真实 API Runtime Evidence。
```

本任务完成后，再重新判断：

```text
P2-2 = CLOSED
```

---

# 1. Current Problem

当前 `run-accept` 的执行顺序大致是：

```text
openPath
↓
sharedSteps
↓
acceptOne
↓
targetRuntimeStart = Date.now()
↓
capture Runtime Snapshot
↓
trigger
↓
Tracking Actual
↓
targetRuntimeEnd
↓
resolve API DataDep
```

而 API Resolver 当前只接受：

```text
targetRuntimeStart <= response.t <= targetRuntimeEnd
```

因此，如果 API 在 `sharedSteps` 阶段已经返回：

```text
sharedSteps
↓
API response   ← 当前会被排除
↓
targetRuntimeStart
↓
trigger
```

最终可能错误得到：

```text
RUNTIME_API_NOT_CAPTURED
```

即使真实业务数据已经存在。

---

# 2. Root Cause

问题不在：

```text
DataDep Contract
```

也不在：

```text
API Resolver selector
```

而在：

```text
Runtime Evidence Window 边界
```

当前：

```text
API Evidence Window
=
target trigger 前很短一段
→ trigger 后
```

实际上应该覆盖：

```text
构建当前 target 业务状态
→
真正触发 target
```

因此 API Evidence Window 必须包含：

```text
sharedSteps
```

期间产生的 API response。

---

本任务只修改：

```text
API Runtime Evidence Window
```

不要修改：

```text
P2-1 DataDep Contract
P2-1.1 Runtime Selector Contract
URL Resolver 语义
User Resolver 语义
Page Resolver 语义
API selector contract
Expected / Actual Compare 规则
accept-chain contract
```

# 4. Required Execution Model

修改后的 target 运行时模型必须是：

```text
开始当前 Path / Target 的业务状态构建
↓
apiRuntimeStart
↓
sharedSteps
↓
API responses
↓
capture URL/window Snapshot
↓
trigger
↓
Tracking Actual
↓
apiRuntimeEnd
↓
resolve API DataDeps
```

因此：

```text
URL / window Expected
```

仍然读取：

```text
sharedSteps 完成后
trigger 前
```

但是：

```text
API Runtime Evidence
```

读取时间范围应为：

```text
sharedSteps 开始前
→
target trigger 执行完成后
```

不要把 URL/window Snapshot 时间一起提前。

---

# 5. First-Phase Deterministic Rule

第一阶段直接使用：

```text
apiRuntimeStart
=
当前 path 的 sharedSteps 开始前
```

每个 target 的：

```text
apiRuntimeEnd
=
当前 target Runtime Compare 前
```

API Resolver 使用：

```text
apiRuntimeStart <= response.t <= apiRuntimeEnd
```

---

# 6. Path-Level API Store

继续保持：

```text
API Collector = browser context level
```

不要改回 page level。

继续使用：

```text
path-level accumulated API store
```

例如：

```js
{
  responses: [...]
}
```

可以在进入新的 path 时：

```text
resetApiRuntimeStore()
```

但不要在每个 target 开始前清空。

原因：

```text
sharedSteps 产生的 response
必须仍然存在
```

---

# 7. Required run-accept Change

当前类似：

```js
async function openPath(...) {
  resetApiRuntimeStore(apiStore)

  await gotoSeed(...)

  for (...) {
    await runStep(...)
  }

  return {}
}
```

需要让 `openPath` 返回 API Runtime 起点。

建议：

```js
async function openPath(...) {
  resetApiRuntimeStore(apiStore)

  const apiRuntimeStart = Date.now()

  await gotoSeed(...)

  for (...) {
    await runStep(...)
  }

  return {
    apiRuntimeStart
  }
}
```

注意：

```text
apiRuntimeStart
```

必须早于可能触发 API 的 `sharedSteps`。

如果 `gotoSeed()` 本身产生的 API 不应纳入当前业务状态，则可以把时间点放在：

```text
gotoSeed 完成后
sharedSteps 开始前
```

优先采用这个边界：

```text
gotoSeed
↓
apiRuntimeStart
↓
sharedSteps
```

这样不会把页面初始化无关 API 大量带入当前 target。

---

# 8. Recommended Boundary

正式采用：

```text
gotoSeed 完成
↓
apiRuntimeStart = Date.now()
↓
sharedSteps
↓
target
```

不要采用：

```text
进入 browser context 时
```

因为窗口过大。

也不要继续采用：

```text
sharedSteps 完成后
```

因为会漏掉业务 API。

---

# 9. acceptOne Input

`acceptOne` 不再自己决定 API Evidence 起点。

当前：

```js
const targetRuntimeStart = Date.now()
```

可以继续用于：

```text
URL/window snapshot timestamp
```

但 API Resolver 不应再把它作为 API 起点。

建议 runtime 参数变成：

```js
{
  apiStore,
  apiRuntimeStart
}
```

然后：

```js
const apiRuntimeEnd = Date.now()
```

在 target 执行完成后生成。

---

# 10. Runtime Context

修改后传给 Resolver 的 context 建议：

```js
{
  apiRuntimeStart,
  apiRuntimeEnd,

  urlSnapshot,
  windowSnapshot,

  api: apiStore
}
```

如果为了兼容现有命名，需要保留：

```text
targetRuntimeStart
targetRuntimeEnd
```

也可以，但必须明确：

```text
API Resolver 使用 apiRuntimeStart/apiRuntimeEnd
```

而不是 URL/window snapshot 的时间点。

优先避免一个字段同时表达两个不同时间语义。

---

# 11. API Resolver Change

当前类似：

```js
function inTargetWindow(item, ctx) {
  return item.t >= ctx.targetRuntimeStart
    && item.t <= ctx.targetRuntimeEnd
}
```

应改成：

```js
function inApiRuntimeWindow(item, ctx) {
  const t = Number(item && item.t) || 0
  const start = Number(ctx && ctx.apiRuntimeStart)
  const end = Number(ctx && ctx.apiRuntimeEnd)

  if (!Number.isFinite(start) || !Number.isFinite(end)) {
    return false
  }

  return t >= start && t <= end
}
```

API candidate 仍然必须满足原有规则：

```text
Runtime Window 内
+
url.includes(dep.api.urlIncludes)
+
HTTP 2xx
+
JSON body parsed
+
field exists
```

不要改变 selector 逻辑。

---

# 12. Multiple Targets in Same Path

同一个 path 中可能有多个 target。

规则：

```text
apiStore
=
path 级累计
```

对于同一路径 target：

```text
Target A
Target B
Target C
```

可以共同使用：

```text
apiRuntimeStart = sharedSteps 开始前
```

但每个 target 有自己的：

```text
apiRuntimeEnd
```

因此：

```text
Target A
→ start ~ A end

Target B
→ start ~ B end
```

Resolver 仍通过：

```text
urlIncludes + field
```

筛选对应 API。

如果因此出现多个不同值：

```text
RUNTIME_API_AMBIGUOUS
```

这是正确结果。

不要为了选“最近一次”而增加业务猜测。

---

# 13. Do Not Add Heuristics

禁止：

```js
取离 trigger 最近的 API
```

禁止：

```js
取最后一个 API，不管值是否冲突
```

禁止：

```js
根据 paramKey 判断 API
```

禁止：

```js
根据 eventName / evtId 判断 API
```

禁止：

```js
读取 expression/sourcePath 来缩小 API
```

如果：

```text
多个候选 API
+
field value 不一致
```

继续返回：

```text
RUNTIME_API_AMBIGUOUS
```

这代表 DataDep selector 精度不足，应回到 P2-1，而不是 P2-2 猜。
