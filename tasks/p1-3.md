# P1-3 Parameter Validation Gate Closure

## 1. 目标

P1-3 解决的问题是：

> Parameter Resolution 已经得到 `expression / sourcePath / evidence / scopeReachable / confidence / unresolved` 后，什么条件下参数才允许进入代码实现。

P1-3 不再解决：

* 参数应该去哪里找
* sourcePath 如何推理
* confidence 如何计算
* Runtime Actual 如何校验
* dataDeps Runtime Resolver 如何执行

这些分别属于：

```text
P1-1 Parameter Resolution Contract
P1-2 Confidence Determinism Closure
后续 Runtime / Acceptance 阶段
```

P1-3 的职责只有一个：

```text
将参数事实转换成确定性的落码门禁。
```

目标链路：

```text
Parameter Resolution
↓
impl.json parameter facts
↓
validate-parameters
↓
READY / NEEDS_CONFIRM / INVALID
↓
event-level gate
├─ READY
│  ↓
│  Implementation
│
├─ NEEDS_CONFIRM
│  ↓
│  人工补充事实
│  ↓
│  re-validate
│
└─ INVALID
   ↓
   返回 Resolution / Static Analysis 修复
```

---

# 2. 当前正式主链路

P1-3 不新增新的事实层，也不修改当前正式主链路。

仍然是：

```text
events.json
↓
adaptor.json
↓
代码定位 + 参数来源追踪
↓
impl.json
↓
validate-impl
↓
needsConfirm Gate
├─ true
│  ↓
│  人工确认 / 修正
│
└─ false
   ↓
   代码实现
↓
build-accept-chain
↓
accept-chain.json
↓
run-accept
```

P1-3 应当增强：

```text
validate-impl
+
needsConfirm Gate
```

不要新增：

```text
parameter-validation.json
parameter-gate.json
```

等新的平行事实文件。

---

# 3. P1-3 的核心原则

## 3.1 Agent 不得自行决定参数是否可落码

禁止：

```text
Agent 看到 confidence=high
↓
自行判断“应该没问题”
↓
直接修改代码
```

必须改为：

```text
Agent 生成事实
↓
validator 计算 gate result
↓
只有 READY 才允许实现
```

---

## 3.2 confidence 不是最终 Gate

以下条件不成立：

```text
confidence = high
=> 可以自动落码
```

正确逻辑是：

```text
confidence = high
只是 READY 的必要条件之一
```

最终 READY 必须同时满足：

```text
expression 已确定
+
sourcePath 合法
+
evidence 合法
+
scopeReachable = true
+
confidence = high
+
confidence 与 evidence 一致
+
unresolved = []
+
expression 可静态验证
+
无 validation error
```

---

## 3.3 业务不确定与结构错误必须区分

P1-3 必须存在三个状态：

```text
READY
NEEDS_CONFIRM
INVALID
```

不能只使用：

```text
true / false
```

三者含义：

| status        | 含义              | 后续                  |
| ------------- | --------------- | ------------------- |
| READY         | 参数事实已闭环         | 可以进入 implementation |
| NEEDS_CONFIRM | 事实不足，但不存在确定性错误  | 人工补充业务事实            |
| INVALID       | 当前事实存在结构错误或证据矛盾 | 返回上游重新解析            |

---

# 4. Parameter 输入 Contract

P1-3 不负责生成参数事实，只消费已有参数事实。

每个参数建议至少包含：

```json
{
  "name": "house_code",
  "required": true,
  "expression": "houseCode",
  "sourcePath": [],
  "evidence": [],
  "scopeReachable": true,
  "confidence": "high",
  "unresolved": []
}
```

具体字段名称应优先兼容当前 repository 中已经存在的 Schema。

Codex / Cursor 不得为了实现本任务随意重构整个 `impl.json`。

如果当前字段命名与本文不同：

```text
优先复用现有字段
```

只有确实缺少表达能力时才最小化扩展 Schema。

---

# 5. Validation Pipeline

每个 parameter 必须依次经过以下检查：

```text
1. Completeness Validation
↓
2. Evidence Validation
↓
3. SourcePath Validation
↓
4. Scope Reachability Validation
↓
5. Expression Validation
↓
6. Transform Validation
↓
7. Confidence Consistency Validation
↓
8. Unresolved Gate
↓
9. Final Status
```

这些步骤必须由确定性程序完成。

---

# 6. Completeness Validation

## 6.1 Required Parameter

当：

```text
required = true
```

且当前参数准备进入代码实现时，必须具备：

```text
name
expression
sourcePath
evidence
scopeReachable
confidence
unresolved
```

其中：

```text
expression != null
sourcePath 非空
evidence 非空
```

否则不能 READY。

---

## 6.2 Required 参数缺 expression

例如：

```json
{
  "name": "house_code",
  "required": true,
  "expression": null
}
```

如果原因是：

```text
业务来源尚未确认
```

应：

```text
NEEDS_CONFIRM
```

如果同时存在：

```text
confidence = high
```

则说明事实内部矛盾，应：

```text
INVALID
```

---

## 6.3 Optional Parameter

`optional` 的含义是：

```text
允许不传
```

不是：

```text
允许猜一个值传入
```

因此，如果 optional parameter 无法确认：

```json
{
  "required": false,
  "expression": null
}
```

可以允许整体继续，但必须明确：

```text
当前参数被省略
```

不要为了填满参数而生成一个未经验证的 expression。

---

# 7. Evidence Validation

## 7.1 Evidence 必须是结构化事实

Evidence 不能只是一段自由文本，例如：

```json
{
  "reason": "感觉这里应该是 houseCode"
}
```

不允许作为可落码依据。

应优先使用明确的 evidence type。

例如：

```text
sameComponentSameField
samePageSameField
localSymbol
propsChain
stateHookChain
apiDataFlow
urlDataFlow
userContext
manualConfirmation
historicalImplementation
semanticHint
modelInference
```

最终字段名以当前 repository Schema 为准。

---

## 7.2 Strong Evidence 与 Weak Evidence

需要固定 strong / weak 分类，禁止 Agent 临时解释。

建议：

### Strong Evidence

可支持自动落码：

```text
sameComponentSameField
localSymbol
verifiedPropsChain
verifiedStateHookChain
verifiedApiDataFlow
verifiedUrlDataFlow
manualConfirmation
```

前提是同时满足：

```text
scopeReachable = true
```

---

### Context / Weak Evidence

只能用于辅助分析：

```text
samePageSameField
historicalImplementation
eventNameSemantic
documentDescription
namingSimilarity
modelInference
```

这些证据不能单独导致：

```text
READY
```

---

## 7.3 规则应代码化

不要在 Prompt 中写：

```text
请综合判断证据是否足够强
```

应在 validator 中建立固定映射。

示例：

```js
const STRONG_EVIDENCE_TYPES = new Set([
  'sameComponentSameField',
  'localSymbol',
  'verifiedPropsChain',
  'verifiedStateHookChain',
  'verifiedApiDataFlow',
  'verifiedUrlDataFlow',
  'manualConfirmation'
])
```

实际类型名称以当前代码中的 enum 为准。

---

# 8. SourcePath Validation

Parameter 的 `sourcePath` 表示：

```text
原始数据来源
→
中间数据传递
→
目标埋点位置
```

validator 至少检查：

```text
sourcePath 存在
sourcePath 非空
sourcePath 节点格式合法
sourcePath 不包含非法空节点
```

如果当前项目已经有静态图 / symbol reference / component relation 能力，则进一步检查：

```text
相邻节点是否存在可证明关系
```

如果目前静态分析能力还不能完全判断整条链路：

```text
不要为了 P1-3 实现一个巨大 AST 系统
```

应按现有能力最小实现。

无法确定的部分：

```text
不得标记 READY
```

---

# 9. Scope Reachability Validation

这是 P1-3 的硬门禁。

必须满足：

```text
scopeReachable === true
```

才允许 READY。

原因：

```text
其它地方存在某变量
≠
当前 targetFunction 可以访问该变量
```

例如：

```text
Page
└─ const houseCode
   └─ ChildA
```

并不能证明：

```text
SiblingComponent
```

中的埋点可以直接使用：

```js
houseCode
```

---

## 9.1 scopeReachable = false

明确不可达：

```text
INVALID
```

建议 code：

```text
PARAM_SCOPE_UNREACHABLE
```

---

## 9.2 scopeReachable 未知

例如：

```text
null
undefined
unknown
```

说明当前事实没有闭环：

```text
NEEDS_CONFIRM
```

或者返回上游做进一步静态分析。

禁止：

```text
unknown => 默认 true
```

---

# 10. Expression Validation

Expression 必须满足两类要求。

## 10.1 Expression 非空

required parameter：

```text
expression != null
```

---

## 10.2 Expression 中的 symbol 必须真实存在

例如：

```js
houseCode
props.houseCode
data.houseCode
```

validator / static analyzer 应尽可能确认：

```text
root symbol 真实存在
且
在 insertion point 对应作用域可访问
```

禁止生成：

```js
houseInfo.houseCode
```

但源码没有：

```text
houseInfo
```

---

## 10.3 不要求 P1-3 自建完整 JS parser

如果仓库当前已有：

```text
AST
parser
symbol resolver
scope analyzer
```

应复用。

如果没有，应优先：

```text
使用项目已有 parser dependency
+
最小静态验证
```

不要通过正则模拟完整 JavaScript scope。

---

# 11. Transform Validation

以下 expression 都属于 transform：

```js
houseCode || '-'
Number(houseCode)
String(houseCode)
Boolean(flag)
type === 1 ? 'A' : 'B'
list.join(',')
```

transform 不能由 Agent 随意添加。

必须有：

```text
transform evidence
```

例如：

```json
{
  "expression": "houseCode || '-'",
  "transform": {
    "kind": "fallback",
    "evidence": [
      {
        "type": "sameComponentSameField"
      }
    ]
  }
}
```

如果：

```text
expression 存在 transform
```

但：

```text
无 transform evidence
```

则：

```text
NEEDS_CONFIRM
```

建议 code：

```text
PARAM_TRANSFORM_UNVERIFIED
```

如果 transformation 与明确已有规则冲突：

```text
INVALID
```

---

# 12. Confidence Consistency Validation

P1-3 不重新计算 confidence。

confidence 的确定性规则属于 P1-2。

P1-3 只负责检查：

```text
当前 confidence
是否与 P1-2 规则计算结果一致
```

建议复用 P1-2 已实现的 deterministic scorer / resolver。

例如：

```text
declared confidence = high
computed confidence = medium
```

必须：

```text
INVALID
```

建议 code：

```text
PARAM_CONFIDENCE_INCONSISTENT
```

不要：

```text
validator 自动把 high 改成 medium
```

因为这会隐藏上游事实错误。

正确流程：

```text
发现不一致
↓
INVALID
↓
返回 Parameter Resolution 修复
```

---

# 13. Unresolved Gate

规则必须简单明确。

## READY

必须：

```text
unresolved.length === 0
```

---

## unresolved > 0

如果 unresolved 表示：

```text
尚未确认的业务事实
```

则：

```text
NEEDS_CONFIRM
```

如果 unresolved 与当前字段明显矛盾，例如：

```text
expression 已声明
confidence = high
但 unresolved 写着“无法确认字段来源”
```

则：

```text
INVALID
```

validator 应至少检查这类明显矛盾。

---

# 14. READY 判定公式

Parameter 只有同时满足以下条件，才能 READY：

```text
required fields valid
AND
expression 已确定
AND
sourcePath valid
AND
evidence valid
AND
存在至少一个允许自动落码的 strong evidence
AND
scopeReachable === true
AND
expression symbol 可验证
AND
transform 已验证（如果存在）
AND
confidence === high
AND
confidence 与 P1-2 结果一致
AND
unresolved.length === 0
AND
无 validation error
```

伪代码：

```js
function isReady(parameter) {
  return (
    hasValidRequiredFields(parameter) &&
    parameter.expression != null &&
    hasValidSourcePath(parameter) &&
    hasValidEvidence(parameter) &&
    hasStrongEvidence(parameter) &&
    parameter.scopeReachable === true &&
    isExpressionValid(parameter) &&
    isTransformValid(parameter) &&
    parameter.confidence === 'high' &&
    isConfidenceConsistent(parameter) &&
    parameter.unresolved.length === 0
  )
}
```

---

# 15. NEEDS_CONFIRM 判定

以下情况进入：

```text
NEEDS_CONFIRM
```

典型包括：

```text
confidence = medium
scopeReachable = unknown
缺少 strong evidence
required expression 尚未确认
transform 缺少业务依据
仍存在业务 unresolved
存在多个候选来源且无法唯一确定
```

前提是：

```text
当前数据不存在确定性的结构错误
```

---

# 16. INVALID 判定

以下情况属于 INVALID：

```text
Schema 不合法
required 字段缺失且数据自相矛盾
scopeReachable = false
expression 引用了不存在的 symbol
sourcePath 明确断裂
evidence 引用不存在对象
confidence 与 P1-2 deterministic result 冲突
confidence=high 但事实不满足 high 条件
已有 expression 与 unresolved 明确冲突
非法 evidence type
非法 transform type
```

INVALID 不能通过人工简单“确认一下”绕过。

必须返回上游修复事实。

---

# 17. Validation Result Contract

不要只输出字符串。

建议返回：

```json
{
  "status": "NEEDS_CONFIRM",
  "issues": [
    {
      "code": "PARAM_STRONG_EVIDENCE_MISSING",
      "level": "confirm",
      "field": "house_code",
      "message": "No strong evidence can prove the expression for automatic implementation."
    }
  ]
}
```

其中：

```text
status:
READY
NEEDS_CONFIRM
INVALID
```

建议 issue level：

```text
info
confirm
error
```

但真正 Gate 逻辑必须根据：

```text
code / status
```

而不是自由文本 message。

---

# 18. Error Code

P1-3 至少固定以下 codes：

```text
PARAM_EXPRESSION_MISSING
PARAM_SOURCE_PATH_MISSING
PARAM_SOURCE_PATH_INVALID
PARAM_SOURCE_PATH_BROKEN

PARAM_EVIDENCE_MISSING
PARAM_EVIDENCE_INVALID
PARAM_STRONG_EVIDENCE_MISSING

PARAM_SCOPE_UNKNOWN
PARAM_SCOPE_UNREACHABLE

PARAM_SYMBOL_NOT_FOUND
PARAM_EXPRESSION_INVALID

PARAM_TRANSFORM_UNVERIFIED
PARAM_TRANSFORM_INVALID

PARAM_CONFIDENCE_INCONSISTENT

PARAM_UNRESOLVED_REMAINING
PARAM_FACT_CONFLICT
```

可以根据当前代码结构补充，但不要随意改名造成同义 code 泛滥。

---

# 19. Event-Level Gate

最终不能只看单个 parameter。

需要汇总到 event / impl item。

规则：

```text
任意 required parameter = INVALID
→ event = INVALID

否则任意 parameter = NEEDS_CONFIRM
→ event = NEEDS_CONFIRM

否则
→ event = READY
```

同时 location / lifecycle 等已有 Gate 应共同参与。

推荐最终逻辑：

```text
event status =
maxSeverity(
  location status,
  lifecycle status,
  parameter statuses
)
```

严重程度：

```text
INVALID
>
NEEDS_CONFIRM
>
READY
```

---

# 20. needsConfirm 派生规则

`needsConfirm` 不应再由 Agent 自由写入。

建议：

```js
implItem.needsConfirm =
  validation.status === 'NEEDS_CONFIRM'
```

如果：

```text
validation.status === INVALID
```

则：

```text
implementation 必须被阻断
```

不要：

```text
INVALID => needsConfirm=true => 用户点一下继续
```

因为：

```text
INVALID
```

代表事实错误，不是事实缺失。

---

# 21. validation 字段归属

推荐：

```text
validation 是 deterministic validator 的运行结果
```

不是 AI 输出。

即：

```text
AI / static analysis 输出事实：
expression
sourcePath
evidence
scopeReachable
confidence
unresolved

validate-impl 输出：
status
issues
```

如果当前 `impl.json` 需要保存 validation：

```json
{
  "validation": {
    "status": "READY",
    "issues": []
  }
}
```

也必须由：

```text
validate-impl
```

生成或刷新。

Agent 不得直接声明：

```json
{
  "validation": {
    "status": "READY"
  }
}
```

并跳过 validator。

---

# 22. 人工确认闭环

当：

```text
status = NEEDS_CONFIRM
```

人工确认不能只产生：

```text
confirmed = true
```

人工确认必须补充新的事实。

例如：

```json
{
  "type": "manualConfirmation",
  "field": "house_code",
  "expression": "props.houseCode",
  "reason": "Confirmed by user based on business semantics"
}
```

然后：

```text
更新 impl.json
↓
重新运行 P1-2 confidence calculation
↓
重新运行 validate-impl
↓
重新得到 READY / NEEDS_CONFIRM / INVALID
```

禁止：

```text
用户确认
↓
直接绕过 validator
↓
implementation
```

# 24. 推荐核心 API

可以收敛为：

```ts
validateParameter(parameter, context)
```

返回：

```ts
type ParameterValidationResult = {
  status: 'READY' | 'NEEDS_CONFIRM' | 'INVALID'
  issues: ValidationIssue[]
}
```

其中：

```ts
type ValidationIssue = {
  code: string
  level: 'info' | 'confirm' | 'error'
  field?: string
  message?: string
}
```

---

# 25. 推荐执行逻辑

伪代码：

```js
function validateParameter(parameter, context) {
  const issues = []

  validateCompleteness(parameter, issues)
  validateEvidence(parameter, issues)
  validateSourcePath(parameter, context, issues)
  validateScopeReachability(parameter, issues)
  validateExpression(parameter, context, issues)
  validateTransform(parameter, issues)
  validateConfidenceConsistency(parameter, context, issues)
  validateUnresolved(parameter, issues)

  if (hasError(issues)) {
    return {
      status: 'INVALID',
      issues
    }
  }

  if (hasConfirmIssue(issues)) {
    return {
      status: 'NEEDS_CONFIRM',
      issues
    }
  }

  return {
    status: 'READY',
    issues
  }
}
```

注意：

```text
READY 不应通过“没有 error”自动得出。
```

应该显式检查 READY 的所有正向条件。

---

# 26. validate-impl 集成

现有：

```text
validate-impl
```

必须调用 Parameter Validation Gate。

例如：

```text
validateImpl
├─ schema validation
├─ target validation
├─ lifecycle validation
├─ parameter validation    ← P1-3
└─ final gate aggregation
```

统一命令执行：

```bash
validate-impl <impl.json>
```

时必须包含 P1-3。

不要额外要求用户记住：

```bash
validate-parameters
```

才能得到正确 Gate。

如果内部需要拆命令用于测试可以保留，但正式 workflow 应只有一个入口。

---

# 27. Workflow Gate

正式 workflow 在进入 implementation 前必须检查：

```text
validation.status
```

只有：

```text
READY
```

才允许进入实现阶段。

伪代码：

```js
if (impl.validation.status === 'INVALID') {
  throw new Error('Implementation blocked: invalid impl facts')
}

if (impl.validation.status === 'NEEDS_CONFIRM') {
  return enterHumanConfirmationGate()
}

runImplementation()
```

不能只检查：

```text
needsConfirm === false
```

而忽略 INVALID。

---

# 28. 测试要求

P1-3 必须增加确定性测试。

至少覆盖以下 case。

---

## Case 1：完整强证据

```text
expression 有值
sourcePath 完整
strong evidence 存在
scopeReachable=true
confidence=high
unresolved=[]
```

Expected：

```text
READY
```

---

## Case 2：medium confidence

Expected：

```text
NEEDS_CONFIRM
```

---

## Case 3：high + unresolved

Expected：

```text
NEEDS_CONFIRM
```

如果 unresolved 与 high 明显冲突：

```text
INVALID
```

具体以 P1-2 Contract 为准。

---

## Case 4：scopeReachable=false

Expected：

```text
INVALID
```

---

## Case 5：scopeReachable unknown

Expected：

```text
NEEDS_CONFIRM
```

---

## Case 6：只有 weak evidence

# 31. Agent Contract

Codex / Cursor 在实现本任务时必须遵守：

```text

2. 识别当前 impl schema、P1-1、P1-2、validate-impl 实现。

7. 不允许 Agent 自己决定 READY。

10. INVALID 不允许通过人工确认直接绕过。
11. 正式 validate-impl 必须执行 Parameter Validation。
12. 增加 deterministic tests。
13. 所有新增规则尽量 enum / constants / script 化，不放在 Prompt 中自由解释。
```

# 36. P1 系列完成后的 Parameter Closure

P1-1、P1-2、P1-3 最终组成：

```text
P1-1
Parameter Resolution Contract
参数怎么找、证据怎么记录
        ↓
P1-2
Confidence Determinism
同样事实如何得到同样 confidence
        ↓
P1-3
Parameter Validation Gate
什么条件才允许进入 implementation
        ↓
Validated impl.json
        ↓
Implementation
```

最终原则：

> Agent 负责发现和解释参数事实；确定性程序负责判断这些事实是否足以支持代码实现。任何无法证明的参数不得通过猜测补齐，任何业务不确定进入人工 Gate，任何结构性错误直接阻断实现。
